## Upstream reuse and deletion decisions

The complete upstream range contains 110 commits: the previously reviewed
92 and 18 new commits. The [commit inventory](../0.0.1-source-20261030/upstream-review.tsv)
records every commit and review provenance, including merge envelopes.
The earlier review is preserved at
`/home/francis/bark-integration-2026-10-01/upstream-rebase-review-20261029/`.
Its wallet and server reports, resolution log and changed-patch replay map
remain evidence under their original source identity, not fresh execution.

The final source adopts upstream guarded action checkpoints, mandatory
recovery-post authentication, typed Lightning states, daemon URL discovery,
checked fee arithmetic, response-compression removal, covering database index,
settlement retries, fee startup clamping and request caps. The new thin CLI
does not replace the shipped legacy `bark` binary by assumption.

The new range adds concrete token-filter enforcement, system DNS caching,
scheduled-round validation, recoverable mid-round input exits, actual-source
revocation, refused-payment unlinking, post-promotion hold-cancel handling,
late-xpay attempt binding, board-exit binding and offboard capacity limits.
Their actual code and coupled test changes were inspected. A source inspection
does not establish an executed exploit or test pass.

This integration removes the custom SQL `EXISTS` receive selector and uses
upstream's `get_latest_payment_attempt_by_htlc_vtxos`. Cancellation receives the
specific subscription ID instead of resolving the latest same-hash receive.
The fork's complete per-source finality checks remain inside the write
transaction; upstream's latest-attempt lookup is not a substitute for those.

Upstream now returns the inserted attempt ID. The successful payment path
uses that value directly instead of reading the whole attempt back, and the
xpay call takes the upstream ID argument. Error handling retrieves only the
same attempt, with an explicit ID check. The shared upstream payment column
list replaces repeated query projections. A sender-mailbox query by primary
key no longer sorts or limits a unique row.

Fallback registration no longer verifies the same signature at both the RPC
handler and database method. The database method still verifies before the
insert and verifies the canonical concurrent winner. Decode and immutable
destination checks remain. No alternate registration path bypasses that check.

The existing atomic subscription promotion stays. Upstream's separate
promotion does not supply Scuttle's same-transaction funding/expiry fence.
An unsuccessful promotion records no funding link; a post-promotion backend
error must not pretend the issued receive never existed. Upstream's corrected
hold-cancel handling is retained.

## Fork necessity and slop review

The [path-by-path rationale](../0.0.1-source-20261030/fork-rationale.tsv)
covers all 250 retained paths relative to fixed upstream. It is a disposition
inventory, not 238 independently executed tests. Generated code and test-only
changes are identified separately from runtime functionality.

The review traced the actual authorization, admission, checkpoint, source
selection, allocation and broadcast paths. It challenged these large areas:

| Retained area | Concrete requirement and rejected shortcut |
| --- | --- |
| Joint owner link and address codec | A coin-key signature must not select another registered mailbox without matching consent. Generic mailbox registration/recovery authentication does not bind that coin. Existing secp256k1 and blinding primitives are used; no new crypto library. |
| Legacy evidence and exact-operation replay | Already issued offline rights cannot manufacture a new mailbox signature. Legacy decoding and exact accepted-operation replay preserve those obligations without permitting new coin-only issuance. |
| Immutable fallback records | The authorized wallet/mailbox chooses any supported Bitcoin script. No Bitcoin-key, human-identity, xpub-root or common-seed proof is introduced. |
| Source-linked Lightning outcomes | Same-hash attempts can have different owners and outcomes. Upstream native bookkeeping tables and a preimage alone do not identify the complete paying source set. |
| Economic cut, entitlement and allocation | A signed ancestor is not additional customer principal. Every current terminal, sibling, anchor, fee and irreversible spend must conserve backing before payout. No upstream automatic fallback allocator replaces this. |
| Completed-view generation and reorg rebuild | captaind and watchmand are separate processes. A cached tip or process-local lock cannot prove both completed the same canonical view after restart/reorg. |
| Pending/adopted wallet projection | Return, same-store recovery, another device and payout reorg must not erase claims, credit unsigned history or resurrect paid coins. Two sets retain this exceptional projection; they do not create a second payment ledger. |
| Immutable parent and operator fee child | Fee replacement must not change customer destinations/amounts. The existing upstream CPFP builder is extended for verified orphan-child replacement; no parallel wallet or fee budget is added. |
| Stable typed refusals | SDK, REST and generated clients need an authoritative rejection reason. Diagnostic text, a generic 404 or a test counter cannot establish financial terminality. |
| CLN correction | The approved one-assignment terminal route-error correction remains exact. The unbuilt CLN fork pin stays separate. Version 26.06.7 is not selected. |

No new compatibility framework, simulator, service, instrumentation layer or
production dependency was added. The coordinator's seven-line diagnostic
xpay logging patch was inspected and excluded. The original uncommitted H09
fixture was copied as source evidence, not silently promoted into a passing
regression. Existing scale limits and ordinary 180-second, zero-retry checks
were not weakened. No original regression body was deleted to make the merge
appear green.

## Migration implications

All 123 existing server/wallet migration files in the f34 input are byte
identical. In particular, deployed server V73 and wallet migration 43 are not
rewritten. Mapped upstream payloads retain fork versions V74 through V77;
joint authorization retains V78. No migration history row or checksum is
fabricated, and legacy ownership rows remain version 1 without invented consent.

Upstream's new `V77__board_exit.sql` becomes additive fork
`V79__board_exit.sql`, with an identical payload. It records one exit txid per
funding outpoint and script. Existing issued alternate Bitcoin signatures
cannot be retroactively revoked by this table. A new fee/delta cannot obtain a
different exit after an earlier cosign; keep the original signed checkpoint.
The generated schema mirror includes the table, but final regeneration is
still pending.

This lineage is for supported Scuttle stores. It does not claim that an
unrelated upstream V77 database can use Scuttle migration numbers directly,
or that old experimental overlay formats are converted. The previous copied
V73-to-V77 and V77-to-V78 results remain historical components. A copied
V78-to-V79 upgrade and post-upgrade operations are not executed here.
